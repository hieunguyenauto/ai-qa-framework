# Learned rules — test design (the AI reads this at step 3 of the design flow)

## Test design (viewpoints / test cases that were missed)
- D01 Every submit / save button: add a case for double click / repeated Enter while loading → no duplicate records.
- D02 Amount / quantity fields: add boundaries MIN, MAX, 0 and negative numbers — not only typical values.
- D03 Uploads / chat / long text: add cases over the limit (characters, number of images, file size) that must show an error.
- D04 Two parties acting at the same time (one user submits while another completes…): add a race-condition case.
- D05 Status changes: check the old status is cleared and the new one is correct, including continue / redo flows.
- D06 Buttons by role: use the permission matrix of the basic design, never infer from similar-looking UI; test every role.
- D07 UI state must be kept / closed correctly: pagination after Back, dialog after save, read / unread, badges.
- D08 Data in the right context: never open / create data for another shop, record or user.
- D09 Happy path of push / notification / external integrations → always add a failure case; the business data must not be rolled back wrongly.
- D10 Same kind of impact → same assertions across TC groups; multi-step upgrades → test permissions at every intermediate step.
- D11 Before taking a ticket into scope: check the roles it covers, its release phase and its parent / child tickets.
- D12 Check duplicates by content (not only by ID) and trace VP ↔ TC both ways (no empty VP, no TC pointing to a missing VP).
- D13 Test the right layer: a security rule / middleware attached to a route is tested on that route, plus a negative case.
- D14 TCs imported from an outside file (hand-written CSV…): compare every step with the screen catalog / real screen and add mandatory steps that were skipped. (design/2026-10-12-e2e-missing-ui-step.md)
- D15 Master-edit screens with two save levels (row modal → page 'Save'): the TC must write both levels and check the data survives a reload. (design/2026-10-13-two-level-save.md)
- D16 Save followed by a completion dialog ("…が完了しました。" + 'OK'): Steps must say "Verify: dialog '<message>' → 'OK'" before the next step. (design/2026-10-13-save-done-dialog.md)
- D17 Flows taken from a CSV / the mobile app: compare with the web screens (catalog / recon) before LOCK; every condition branch (ON / OFF, category, below / above a limit…) gets its own steps and expected state, never one shared template when TCs are generated by script. (design/2026-10-14-e2e-branch-flow-template.md)
- D18 TCs driven by a record status / approval type: before LOCK inspect the real buttons at every status (Draft / Pending / Rejected / Withdrawn…), the status after each action and the full auto-approval conditions (tax included / excluded, per-level limits, urgent flag, several records); put each Verify at the role that can actually see it. (design/2026-10-16-status-actions-verified.md)
- D19 Forms with default rows / auto-computed cells (quotes, invoices…): Steps say whether default rows are kept or deleted, which cell gets which value and whether totals are tax included or excluded — never only "so that total = …". (design/2026-10-16-form-input-every-field.md)

## Excel / tools
- T01 Google Sheets tab names > 31 characters are renamed on xlsx export → INDIRECT formulas follow the new name.
- T02 FILTER / MAP / LAMBDA do not work in LibreOffice / openpyxl → existing #REF! / #NAME? are not caused by your edit.
- T03 The header row is not fixed → find the literal header (e.g. "TC ID"), never hard-code the row.
- T04 Merged cells → unmerge the target range before writing with openpyxl.
- T05 Text starting with "=" or "=+" is read as a formula → write it as text.
- T06 "Total TCs" at the top of a sheet = number of result cells (TC × role / platform), not the number of TCs.
- T07 Deliverables for reviewers: export a new file, never edit the original.
